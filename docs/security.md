# Security and data handling

- Supabase verifies bearer tokens with `getUser` on each API call. Tokens are not accepted based on client claims alone. Browser requests use Authorization headers, not ambient cookies; state changes do not rely on cross-origin cookie authentication.
- PostgreSQL RLS limits every web query to the verified user. The web role does not bypass RLS; identity is transaction-local and cleared by commit/rollback. All job lookups also use explicit ownership predicates. Anonymous/public Data API access is revoked.
- Quota reservation is a single atomic upsert in the same transaction as job creation; it cannot oversubscribe during concurrent requests. Abandoned uploads still count against the daily submission allowance, limiting abuse. Daily counters reset at midnight UTC and are not refunded on delete.
- An atomic database rate bucket permits at most 90 authenticated API calls per minute per user across Vercel instances. Auth itself should additionally use Supabase's configured limits and CAPTCHA before a broad public launch. Unauthenticated requests cannot allocate uploads.
- Upload URLs are restricted to random pending keys, have ten-minute expiry, and bind content length. Validated uploads are copied to separate source keys that browser upload URLs cannot modify. File extensions are convenience validation; FFprobe is the authoritative format/track validation before submission.
- Originals and outputs remain private. Download URLs are available only for completed, unexpired owned jobs and expire in 60 seconds. An already-issued URL is a bearer capability until it expires or the object is deleted; application cancellation cannot retroactively revoke that URL.
- Provider hosts are allowlisted, redirects are rejected, encoder output URLs are structurally checked, and media parsers permit only local file/pipe protocols. No untrusted filename is passed to a shell. Temporary files use random local directories.
- Tokens and API keys exist only in worker memory/environment. PostgreSQL stores provider job IDs but no provider tokens. Provider errors are converted to safe codes before logging. Do not enable HTTP debug/trace plugins that capture query strings; redact `key`, `auth_token`, `job_otu`, `token`, `jobtoken`, Authorization, and R2 `X-Amz-*` query parameters in external APM/proxy tooling.
- Output arrives through bounded multipart streaming, is checked in R2, then probed and fully decoded from local disk. Only validated results become downloadable. R2 multipart transfers are aborted on failures; lifecycle rules catch transfers abandoned by process death.
- Worker cancellation stops locally managed operations. TikQuick has no documented cancellation or deletion endpoint, so its own retention policy must be disclosed and reviewed before launch. Settings distinguish Forged storage deletion from provider retention.
- Account settings support deleting all video data. Authentication-account deletion is an administrator operation after video cleanup; no browser service-role access is implemented. Daily aggregate counters intentionally remain while the account exists.
- Keep Node/Next.js/FFmpeg and dependencies patched. A production threat review, infrastructure permission review, retention agreement with TikQuick, and live acceptance tests remain release responsibilities; automated tests do not establish deployment security by themselves.
